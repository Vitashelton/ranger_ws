## 1. 当前候选题目（暂不冻结）

中文：

> 面向语言导航任务的依赖感知事件触发式局部重规划

英文：

> Dependency-Aware Event-Triggered Local Replanning for Language-Guided Mobile Robots

## 2. 唯一研究问题

当 Habitat-Sim、Gazebo 或真实移动机器人环境发生状态变化时，哪些变化真正影响剩余任务？机器人应当继续执行原计划，还是只修复受影响的最小任务子图？

本文不研究“如何让 LLM 更聪明”，而研究在相同语言模型、Prompt、导航执行器和环境事件下，依赖关系是否能够减少不必要的完整重规划，同时保持任务成功率。

## 3. 核心假设与事件边界

机器人执行一个由语言指令编译得到的有序任务图。不同后端的环境变化通过统一的事实观测/事件证据接口进入重规划器：

```text
event monitor -> structured event -> dependency slicer -> local repair -> Nav2
```

Habitat-Sim负责主要的复杂、批量、标准化实验；Gazebo可以负责：

- 注入可控的环境扰动；
- 产生用于评估的真实事件时间和真实状态；
- 提供机器人、障碍物和导航执行环境。

Ranger负责真实移动机器人迁移验证：MID-360S、D435i和定位系统产生事实证据，Nav2和底盘执行任务原语。

Habitat-Sim/Gazebo的实体真值只用于事件注入、对齐和离线评测；在线算法不能直接读取场景真值或事件标签。若为了隔离规划算法而注入结构化事件，论文必须明确称为“结构化事件接口下的任务重规划实验”，不得包装成感知贡献。Ranger实验则必须通过传感器和事实验证接口产生证据。

事件统一表示为状态谓词的变化：

\[
\Delta S_t=S_t-S_{t-1}.
\]

示例：

```text
reachable(A): true -> false
occupied(B): false -> true
blocked(C): false -> true
reachable(A): false -> true
```

每个事件至少包含：

```json
{
  "event_id": "e_017",
  "event_type": "LOCATION_UNAVAILABLE",
  "changed_predicates": ["reachable(A)=false"],
  "scope": ["A"],
  "timestamp": 42.5,
  "source": "event_interface"
}
```

## 4. 任务图表示

LLM 只在任务开始时把自然语言转换为严格 JSON 任务图；任务图随后由验证器检查，并由确定性的依赖切片器和局部修复器处理。

任务图为 DAG。每个节点必须包含：

- `id`：节点唯一标识；
- `action`：任务原语；
- `target`：目标位置或目标对象；
- `preconditions`：执行前必须成立的状态谓词；
- `success_conditions`：任务完成条件；
- `failure_states`：节点失败时产生的状态谓词；
- `depends_on`：直接依赖节点列表。

示例任务：

```json
{
  "task_id": "inspect_route_01",
  "nodes": [
    {
      "id": "reach_A",
      "action": "navigate",
      "target": "A",
      "preconditions": ["reachable(A)"],
      "success_conditions": ["at(A)"],
      "failure_states": ["unreachable(A)"],
      "depends_on": []
    },
    {
      "id": "inspect_A",
      "action": "inspect",
      "target": "A",
      "preconditions": ["at(A)"],
      "success_conditions": ["inspected(A)"],
      "failure_states": ["inspection_failed(A)"],
      "depends_on": ["reach_A"]
    },
    {
      "id": "reach_B",
      "action": "navigate",
      "target": "B",
      "preconditions": ["reachable(B)"],
      "success_conditions": ["at(B)"],
      "failure_states": ["unreachable(B)"],
      "depends_on": ["inspect_A"]
    },
    {
      "id": "inspect_B",
      "action": "inspect",
      "target": "B",
      "preconditions": ["at(B)"],
      "success_conditions": ["inspected(B)"],
      "failure_states": ["inspection_failed(B)"],
      "depends_on": ["reach_B"]
    },
    {
      "id": "return",
      "action": "navigate",
      "target": "start",
      "preconditions": ["inspected(B)", "reachable(start)"],
      "success_conditions": ["at(start)"],
      "failure_states": ["unreachable(start)"],
      "depends_on": ["inspect_B"]
    }
  ]
}
```

第一版只保留 6 个任务原语：

```text
navigate, inspect, confirm, wait, return, stop
```

不实现开放式行为树、任意工具调用或低层速度控制。

## 5. 依赖切片算法

设当前任务图为 \(G_t=(V_t,E_t)\)，已完成前缀为 \(P_t\)，未完成节点为 \(U_t\)。若边 \(u\rightarrow v\) 表示“节点 \(v\) 依赖节点 \(u\)”，先找出直接受事件影响的种子节点：

\[
A_t=\{v\in V_t:\Delta S_t\cap(Pre(v)\cup Req(v)\cup Eff(v))\neq\varnothing\}.
\]

对种子节点取任务依赖图中的下游闭包：

\[
R_t=Desc_{G_t}(A_t)\cap U_t.
\]

其中：

- `Pre(v)` 是执行前置条件；
- `Req(v)` 是节点依赖的资源、位置和通道条件；
- `Eff(v)` 是节点完成后供后续节点使用的结果；
- `Desc` 是沿依赖边向下游传播的传递闭包；
- `R_t` 是需要重新规划的最小候选子图。

这一定义比“环境有变化就重规划”更严格：与当前任务无关的 C 区域变化不会影响 A、B 任务；若 A 发生变化，则依赖 A 的后续节点会被一起纳入切片。

### 已完成前缀保护条件

已完成前缀不能无条件保留。只有当事件没有破坏已完成节点的完成条件时，才保留该节点：

\[
P_{keep}=\{v\in P_t:\Delta S_t\text{ 不破坏 }Success(v)\}.
\]

如果事件使某个已完成节点失效，则回退到最早失效节点及其下游；否则保留全部已完成前缀。该规则用于避免“局部修复”通过错误保留历史结果而得到虚假的效率提升。

## 6. 决策与局部修复

每次事件只有两个高层决策：

```text
R_t = empty:
    继续执行原计划，不调用 LLM，不重置 Nav2 任务。

R_t != empty:
    保留合法已完成前缀，只对受影响子图生成最小可行修复。
```

局部修复候选集合记为 \(F(R_t)\)，必须同时满足：

- 所有节点前置条件成立；
- 原任务顺序和依赖关系不被非法破坏；
- 已完成且仍然有效的节点不重复执行；
- 修复后仍能达到最终任务目标；
- 不包含低层 `cmd_vel` 或未经验证的控制命令；
- 导航目标能够被当前 Nav2 执行器接受。

选择修复方案：

\[
\delta^*=\arg\min_{\delta\in F(R_t)}
\left[
C_{execution}(\delta)+\lambda C_{edit}(\delta)+\mu C_{API}(\delta)
\right].
\]

其中：

- \(C_{execution}\)：修复后新增导航、等待和动作执行代价；
- \(C_{edit}\)：被修改、插入、删除或回退的任务节点数；
- \(C_{API}\)：LLM 调用次数、Token 数和等待时间；
- \(F(R_t)\)：满足前置条件、依赖、顺序和任务目标的可行修复集合。

当 \(R_t=\varnothing\) 时，\(C_{API}=0\)。局部修复器优先使用确定性候选搜索；LLM 只负责初始任务图编译和局部修复候选生成，不参与底层导航控制。

## 7. LLM 的边界

LLM 只承担两项工作：

1. 将自然语言任务编译为带依赖的 JSON 任务图；
2. 在受影响子图上生成若干候选局部修复。

LLM 不承担：

- 直接输出坐标、速度或 `/cmd_vel`；
- 直接读取 Gazebo 真值；
- 决定是否绕过任务依赖验证器；
- 直接调用 Nav2 之外的低层控制接口。

所有输出必须经过 JSON Schema、任务依赖、前置条件和安全规则验证。实验中固定同一个模型、Prompt、超时、温度和缓存策略，避免把模型差异误认为算法差异。

## 8. 对比方法

| 方法 | 机制 | 是否判断事件相关性 | 是否局部修复 |
| --- | --- | ---: | ---: |
| Open-loop | 初始生成一次，之后不处理环境事件 | 否 | 否 |
| Periodic | 固定周期调用 LLM 生成完整计划 | 否 | 否 |
| Any-change | 任意状态变化都触发完整重规划 | 否 | 否 |
| Failure-only | 只有导航失败才触发完整重规划 | 仅失败 | 否 |
| Local-repair | 直接选取局部节点修复，不做依赖闭包 | 部分 | 是 |
| Ours | 依赖切片 + 事件触发 + 最小可行局部修复 | 是 | 是 |

若预算约束事实验证方向通过新颖性闸门，主实验还必须加入：No-monitor、Always-monitor、Periodic-monitor、Random/nearest-query、Dependency-only query 和一般VOI/监控启发式。旧表中的完整重规划和局部修复方法继续作为计划修复对照，但不能覆盖新的“验证什么、何时验证、何时停止验证”问题。

所有方法必须共享：

- 初始语言指令；
- 初始任务图；
- LLM 模型和 Prompt；
  - 各后端世界、事件时间表和随机种子；
  - Nav2或Habitat任务执行器；
- 任务终止条件。

## 9. Habitat主实验与Gazebo补充场景

Habitat-Sim结合LHPR-VLN/HM3D负责主要的复杂、批量、标准化结果。主实验应覆盖多任务图、多布局、多事件可观测性和多预算，而不是只重复一个 `A -> B` 模板。底层动作可以不同，但所有任务必须先映射到统一的 `navigate / inspect / confirm / wait / return / stop` 原语和事实证据接口。

Gazebo只保留为移动机器人接口调试和补充验证场景：验证事件注入、事实证据适配、导航执行、日志和安全停止。现有 `benchmark_navigation_controller.py` 不得暗中执行自主重规划。AI2-THOR/ProcTHOR只作为兼容性回退或外部复现实验。

只保留三类事件，避免场景扩张：

### 9.1 无关事件

当前任务访问 A、B，C 区域发生障碍或可达性变化。

目标：验证算法不会因为无关变化而调用 LLM 或重置当前导航。

### 9.2 相关但局部事件

B 点暂时不可达、B 被占用或 B 的检查条件失效。

目标：验证只修改 `reach_B -> inspect_B -> return` 必要部分，并保留仍然有效的 A 前缀。

### 9.3 连锁事件

A 的通行条件变化，导致依赖 A 的检查、B 访问和返回节点全部受影响；或者一个通道恢复可用，使先前的局部修复可以停止继续扩展。

目标：验证依赖切片能找到完整受影响闭包，而不是只修复直接报错节点。

主实验不加入：动态语义建图、YOLO、开放式主动探索、新BEV网络、能耗模型、机械臂操作、新 SLAM 或新局部规划器；若候选问题通过新颖性闸门，只实现受任务约束的事实验证动作。

## 10. 评价指标

### 任务效果

- Task Success Rate；
- 任务完成时间；
- 导航失败次数；
- Nav2 goal cancel/restart 次数；
- 路径长度和额外绕行代价。

### 重规划效率

- 无效重规划率：事件与剩余任务依赖无关却触发重规划的比例；
- 漏触发率：事件破坏任务可行性却没有及时修复的比例；
- LLM 调用次数；
- 输入/输出 Token 数；
- API 等待时间和超时次数；
- 修复延迟：事件发生到新可行计划提交的时间。

### 局部性与任务稳定性

- 修改、插入、删除或回退的节点数；
- 受影响节点覆盖率；
- 原计划已完成前缀保留率；
- 任务图编辑距离；
- 错误回退次数。

主要论文结论必须同时满足：任务成功率不显著下降，且 Ours 的无效重规划率、LLM 调用次数、修复延迟或任务图修改规模显著下降。

## 11. 实验协议

正式实验采用配对随机种子：

```text
6 methods × 3 event classes × 20–30 seeds
```

预实验先使用 5–10 个种子，只用于检查协议和实现，不用于最终统计结论。正式实验中所有方法共享同一组事件序列。

建议报告：

- 均值、中位数和 95% 置信区间；
- 配对差值；
- 效应量；
- 失败案例和超时案例；
- 不同事件类型的独立结果。

实机只做小规模迁移验证：使用现有 `ranger_nav`、MID-360S、FAST-LIO 和底盘执行几条“按语言顺序访问目标点”的任务。实机用于验证消息接口、Nav2 执行和相对趋势，不把传感器融合或 SLAM 写成本文算法贡献。

## 13. 算法完成门槛

在开始大规模 Habitat 主实验前，必须通过以下纯 Python 测试：

1. 无关 C 事件得到空切片，且不产生 LLM 调用；
2. B 局部事件得到 B 及其下游依赖闭包；
3. A 事件能够传播到所有依赖 A 的后续节点；
4. 已完成节点仍有效时，前缀完全保留；
5. 已完成节点失效时，回退到最早失效节点；
6. 非法任务图、循环依赖和不满足前置条件的修复全部被拒绝；
7. 六种基线使用同一初始任务图和事件序列，且行为确实不同；
8. 每次实验记录任务图版本、事件序列、LLM 调用、Token、修复延迟和终止状态。

在这些条件完成前，不声称已经有论文级消融结果。

## 14. 明确不做

- 不训练和部署 RangerWM 世界模型；
- 不做 MID-360S 语义建图或 D435i 融合；
- 不做 YOLO、开放式主动探索或新的BEV网络；如果预算约束事实验证通过新颖性闸门，只实现任务条件化的受限验证动作；
- 不新增 SLAM、局部规划器或能耗模型；
- 不让 LLM 输出低层运动控制；
- 不同时维护第二套语言导航、办公室 RPG 或动态语义维护主线；
- 不把 Gazebo 真值输入算法后包装成端到端感知结果。

```text
Habitat任务执行器 / Nav2固定执行器
        ↓
RangerMini 2.0（迁移验证）
```

Habitat-Sim结合LHPR-VLN/HM3D负责复杂、批量、标准化的主要论文实验；Ranger负责证明同一抽象EventSlice决策器能够迁移到真实移动机器人导航；Gazebo负责接口调试、动态导航补充验证和硬件前置联调。AI2-THOR/ProcTHOR保留为兼容性回退或外部复现实验。TCA-BEV只作为可选事件观测前端和消融项，不与EventSlice并列为第二个论文算法。

“同一套算法”指以下算法层对象和逻辑完全共用：任务图Schema、事实/事件表示、验证或触发决策、依赖切片、局部修复器、代价接口和日志协议。Habitat的底层视觉导航动作与Ranger的Nav2目标、传感器消息可以不同，只能由后端适配器转换为统一的 `navigate / inspect / confirm / wait / return / stop` 任务原语和事实证据。算法包中不允许存在按平台分叉的修复逻辑。

### 15.2 开始实现前必须解决的三个接口问题

1. 现有Gazebo世界主要输出 `/scan`、RGB和深度，而 `ranger_nav`/TCA-BEV路径使用 `/livox/lidar`、PointCloud2、`/nav/points` 等接口；必须加明确的适配层，不能靠论文文字假设两者已经一致。
2. 现有 `benchmark_navigation_controller.py` 自带动态绕行和重规划；正式对比前必须改成纯任务/导航目标执行器，或者关闭其自主重规划。
3. `/benchmark/ground_truth/events` 只能用于事件注入和离线评测，不能被在线算法订阅；算法看到的事件必须通过统一观测接口产生。

### 15.3 阶段验收

- 阶段1：纯Python核心测试通过，并证明所有方法共享同一抽象任务图、事实证据和事件序列。
- 阶段2：Habitat/LHPR-VLN完成一条完整任务，能记录部分观测、验证/事件证据、切片、修复、执行和最终状态。
- 阶段3：Habitat/LHPR-VLN先5–10个种子验收协议，再进行覆盖多任务、多布局、多事件可观测性和多预算的正式批量实验。
- 阶段4：Gazebo完成同一抽象接口到移动导航执行器的补充适配验证，不允许现有控制器暗中重规划。
- 阶段5：RangerMini 2.0、MID-360S、D435i、Jetson Orin Nano完成低速小规模迁移演示，并报告延迟、成功率和安全停止。

在阶段3没有完成前，不把符号后端或单回合结果写成Habitat主实验结论；在阶段5没有完成前，不声称已经完成实机验证。

## 16. 新颖性红队审计与路线修订

### 16.1 审计结论

当前 EventSlice 的以下组成不能单独作为论文创新：

- 任务依赖图或因果图；
- 受影响子图切片；
- 保留已执行前缀；
- 局部/稳定计划修复；
- 减少完整重规划和搜索展开；
- 动态事件注入；
- 将LLM限制在初始编译或候选生成环节。

已有计划修复和重规划窗口工作已经讨论计划稳定性与局部适配；已有监控研究已经把监控成本、前置条件失效概率、替代计划价值、传感器准确性和序贯决策纳入模型；PRED已经研究环境反馈下的提前动作修订并包含具身仿真和实机实验；RoboGraph已经将部分观测、空间/时间状态依赖、动态干预、任务图编译和大规模闭环评测结合起来。因此，现有符号实验只能证明实现正确，不能证明论文缺口。

### 16.2 候选升级问题（尚未宣称新颖）

候选方向为：

> 面向语言导航机器人的预算约束任务关键事实验证与依赖感知修复

给定：

- 带依赖关系的语言任务图；
- 不完美、延迟或部分可观测的环境事实；
- 受限的验证预算 (B_t)，其成本可以是感知等待、局部停顿、计算量、运动风险或LLM/API开销；
- 任务失败、修复和继续执行的代价。

机器人每一步不再直接接收“某个事件已经发生”的真值标签，而是在 `continue`、`verify(fact)` 和 `repair(slice)` 之间做决策。验证动作得到带噪观测并更新事实信念；任务依赖图用于估计某个事实对下游任务和修复代价的影响。

一个待验证的抽象目标可以写成：

\[
q^* = \arg\min_{q\in Q(B_t)}
\mathbb{E}\left[
 C_{query}(q)+C_{failure}+C_{repair}\mid o_{1:t},q
\right],
\]

但这个公式本身不是创新。必须进一步给出移动机器人特有的观测动作/传感器模型、任务依赖耦合、在线预算更新和可复现实验，并与一般VOI/监控策略直接比较。

### 16.3 新路线的必要实验

正式实验不能再只是少量任务模板乘大量随机种子。至少需要独立改变：

- 任务图结构和下游依赖深度；
- 事件是否可直接观察、延迟观察或只能通过验证发现；
- 观测噪声和误报/漏报率；
- 查询预算和查询成本；
- 传感器/事实前端（理想结构化、Habitat部分观测、LiDAR/RGB-D简单验证、TCA-BEV可选）；
- Habitat多场景主实验、Gazebo移动导航补充和真实机器人验证。

必须新增或重做的对比至少包括：无监控、全量监控、固定周期监控、事件触发但无预算选择、一般VOI/监控启发式、只修复不验证的EventSlice，以及候选方法。主要指标增加：验证查询数/预算消耗、误验证率、漏验证率、事件发现延迟、验证动作时间/计算占用、任务成功率和修复代价。

### 16.4 现实可行性边界

“查询”优先定义为向Habitat观察接口或现有MID-360S/D435i事件前端请求某个目标区域/任务事实的局部验证，成本由观察机会、等待、算力、停顿或安全风险记录；第一版不做新的视觉网络、不做全套主动探索、不改SLAM和Nav2。若候选方法只能在完美事件接口下成立，或者最终只是给旧切片器增加一个重要性分数，则该路线不通过新颖性闸门。

## 17. Habitat主实验与Ranger迁移的共同抽象

两个平台的底层动作不必相同，但算法输入输出必须相同。统一接口至少包含：

```text
compile_task(language) -> TaskGraph
observe() -> FactBelief / EventEvidence
verify(fact_or_region) -> NoisyObservation + QueryCost
execute(TaskPrimitive) -> ExecutionFeedback
repair(TaskGraph, Evidence, Budget) -> PlanDecision
```

Habitat适配器负责把可见性、物体/区域状态和任务级动作转换为上述接口；Ranger适配器负责把MID-360S、D435i、里程计和Nav2结果转换为上述接口。`repair()` 内部的依赖切片、局部修复、预算决策和验证规则必须共用同一实现。

论文实验应采用以下证据结构：Habitat/LHPR-VLN证明复杂任务分布下的统计优势，Gazebo证明动态移动导航接口可运行，Ranger证明相同抽象决策器能够在真实传感器、定位、Nav2和底盘上闭环执行。不能把三者拼成三个不同算法，也不能把Habitat的底层动作复现程度当作迁移成功标准。

## 18. 仿真平台替代方案审计（2026-08-28）

### 首选：Habitat-Sim + LHPR-VLN/HM3D

LHPR-VLN是较新的长时序视觉语言导航基准，包含3,260个任务，平均约150个任务步骤，使用Habitat-Sim和HM3D场景。Habitat-Sim支持RGB-D、导航网格、自定义动作和高吞吐并行，适合把同一套任务级EventSlice放到复杂场景中批量运行。

但LHPR-VLN不能被直接当作“已经包含动态事件修复”的现成基准。需要自己增加事件注入、部分观测、事件延迟/噪声、事实验证预算和统一日志；先完成单回合smoke test，再锁定版本和场景许可。

### 回退：AI2-THOR + ProcTHOR

ProcTHOR可以生成大规模程序化、可交互房屋，显著缓解固定房间和少量模板问题；但它仍属于AI2-THOR生态，主要解决场景规模和多样性，不解决平台代际问题。因此只作为Habitat安装或数据许可失败时的回退。

### 不作为主平台的候选

- `OmniGibson + BEHAVIOR-1K`：有1000级别家庭活动、丰富物体状态和物理交互，但偏移动操作，接Ranger会引入机械臂和操作执行工作。
- `PARTNR/Habitat`：自然语言任务规模很大，但核心是多智能体协作和家庭操作，不适合直接作为单Ranger导航主基准。
- `NavVerse/Isaac Sim`：更接近连续物理机器人导航，但目前更像新近发布的专项基准，任务重点是室内外连续导航，不是任务级动态事件修复；先观察，不因平台更新就切换主线。
- `EmbodiedCity`：面向城市/空中导航，主体是无人机或城市尺度场景，与Ranger室内轮式导航的迁移关系弱。

当前平台路线冻结为：`Habitat/LHPR-VLN主实验 → Gazebo补充接口 → Ranger实机迁移`。AI2-THOR/ProcTHOR仅保留回退路径。

## 19. 如何利用平台支撑创新点

仿真平台不是论文创新点，而是把算法问题变成可重复证据的实验杠杆。主平台必须同时提供：

1. 多任务图、多布局和不同依赖深度，避免少量任务模板乘随机种子；
2. 同一场景、任务和随机种子下的成对反事实事件，用于比较无关、局部、连锁和恢复变化；
3. 部分观测，使事件不直接以真值标签进入算法，事实可以隐藏、延迟、误报或漏报；
4. 可扫描的验证预算，使查询/观察/停顿/计算成本和任务成功率可以画出曲线。

Habitat/LHPR-VLN主实验外层应实现一个 `EventSliceEnv` 包装器：

```text
LHPR/Habitat task
  -> task graph adapter
  -> progress-triggered counterfactual event
  -> hidden/noisy/delayed fact evidence
  -> finite verification budget
  -> shared EventSlice decision core
```

算法的可发表问题不再是“已知事件后如何切片”，而是：事件不直接告诉机器人、事实观测有成本且预算有限时，应该验证哪个任务关键事实，还是继续执行/立即修复？EventSlice 0.2的依赖切片和局部修复保留为底座；新增部分必须真正改变 `verify(fact)`、继续执行和修复之间的决策，而不是只给节点增加重要性分数。

主实验应报告预算—成功率—任务代价曲线，并使用同一事件的成对反事实结果。Ranger只需把MID-360S/D435i事实证据、Nav2任务执行和真实时间/安全代价接入同一抽象接口，不需要复现Habitat的底层动作。

## 20. 防止基准驱动和结果定制

当前路线不能表述成“找到一个新基准来证明已有算法”。正确关系是：研究问题、抽象接口和评价指标独立成立；Habitat/LHPR只提供规模化任务和场景，事件包装器提供可控反事实，Ranger提供迁移证据。

LHPR-VLN的低层导航轨迹不能直接当作高层任务依赖。正式日志必须分开记录：

```text
N_low  = move/turn等低层动作数
N_high = navigate/inspect/confirm等高层任务节点数
```

如果一个LHPR任务只有2–4个高层子任务，就不能声称它是150节点的任务图。需要通过预先固定的任务生成规则构造6–12个高层导航/检查子任务，并明确称为“基于LHPR的动态事件扩展”，不能冒充LHPR官方任务或官方动态修复评测。

LHPR官方VLN模型、CLIP/BERT/MGDM和训练过程不进入本文主算法。低层路径跟随器、视觉/语义前端和执行器对所有方法固定；若使用Habitat语义真值，论文定位必须写成 `task-level long-horizon navigation repair`，不能写成新的视觉语言导航模型。

选择平台的反事实检验是：即使去掉LHPR，任务级事实验证、事件触发和局部修复的问题仍然成立；如果算法只能依赖LHPR特有的数据格式或动作，就说明是在迁就基准。所有自定义事件、任务图扩展、预算和随机种子必须在实验前固定，并同时报告有利和不利案例。
