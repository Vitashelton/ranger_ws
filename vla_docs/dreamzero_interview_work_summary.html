面试开场版本

我做的不是简单跑一个 checkpoint，而是把 DreamZero 论文里的 WAM 推理机制落到 AgiBot 真机闭环：从三路相机和 GDK 状态采集开始，构造 AgiBot modality schema，经 WebSocket server 进入 DreamZero action head，再把 48 行、22 维动作按 30Hz、row-synced 的方式下发给双臂、夹爪、腰部和底盘，并补齐缓存重置、视频保存、动作日志、推理步数对齐和安全限幅。最终形成了可启动、可调试、可复现实验的 server/client 体系。

面试中可以把工作分成三层讲：第一层是理解论文机制，第二层是补齐缺失工程，第三层是通过日志和真机问题反推系统瓶颈。

论文技术理解

DreamZero 解决什么问题

传统 VLA 更擅长语义泛化，但对新环境中的新物理动作泛化较弱。DreamZero 把视频扩散模型改造成 World Action Model：同一个 DiT 同时预测未来视频和动作，让动作学习从纯状态-动作拟合，变成“生成视觉未来 + 反推动作”的联合建模。

对应论文：Abstract、Section 1、Section 3.1。

模型结构

输入包含视觉上下文、语言指令和 proprioceptive state。视频经 VAE 变成 latent，语言经 text encoder，动作和状态进入 action/state register。DiT 用 flow matching 同时 denoise video latent 和 action latent，最后由 action decoder 输出连续动作。

对应代码：wan_flow_matching_action_tf.py。

为什么是 autoregressive

论文强调 autoregressive WAM 可以保持原始 FPS，不需要像 bidirectional 视频模型那样做严重 subsampling，因此更容易保持 video-action-language 对齐。推理时通过 KV cache 复用历史，执行完一个 chunk 后用真实观测替换预测视频，减轻自回归误差累积。

对应论文：Section 3.1、Appendix B/C、Figure 14。

实时控制约束

AgiBot 设置是 video 5FPS、action 30Hz、action horizon 48，也就是每个 chunk 覆盖 1.6 秒。论文目标是推理和执行异步重叠，理想情况下推理必须在当前 chunk 过期前完成，最终通过 CFG parallelism、DiT caching、torch.compile、kernel/scheduler 优化、Flash 等方式追求 7Hz。

对应论文：Section 3.2、Appendix C/D。

关键问题与解决方式

遇到的问题 根因判断 解决方案 可展示结果
官方没有直接可用的 AgiBot 真机 server/client 论文/权重给的是模型能力，但真机需要明确 observation schema、WebSocket 元数据、机器人 SDK 执行器。 补 AgiBot policy wrapper 和 GDK live client，约定 top_head/hand_left/hand_right、双臂、夹爪、头、腰、底盘的输入输出协议。 服务端 metadata 显示 action_space=agibot_flattened，客户端可连续推理并生成 action JSON。
DROID schema 与 AgiBot schema 不兼容 DROID 是单臂/少量相机，AgiBot 是双臂移动操作，action key 和 state key 完全不同。 在 server wrapper 中显式维护 VIDEO_KEY_MAPPING、STATE_KEY_MAPPING 和 action flatten 顺序。 模型输出统一变成 (48,22)，client 可按维度解析双臂、夹爪、头、腰、底盘。
动作执行被 Ruckig 展开得过慢 模型本来输出 48 行 chunk；Ruckig 插值把每段展开成大量点，导致执行时长从论文假设的 1.6s 拉长到十几秒量级。 实现 direct-48：每个 row 直接下发一次 move_arm，按 direct_control_hz=30 节拍执行；保留限幅、限速、限加速度。 执行流式时长稳定约 1.60s，完整 chunk 约 1.80s，与论文 48/30Hz 对齐。
推理步数和论文/配置不一致 action head 曾经硬编码 num_inference_steps=16，导致 num_inference_timesteps=4 没真正控制 denoising loop。 改为读取 config/checkpoint，server 支持 --num-inference-timesteps，并在 4-step 下禁用 16-step mask 跳步逻辑。 日志能看到 DIT Compute Steps 4，稳态推理从约 6.6s 降到约 2.6-3.0s 的量级。
连续任务后动作不稳定 DreamZero action head 是有状态 causal policy，内部维护 KV cache、cross-attn cache、current_start_frame 和语言状态。 增加 reset_inference_cache()，在 reset、session 切换、连接关闭时让 rank0 和 worker 都清缓存。 减少 prompt 切换/任务切换后继承上轮状态的风险。
三路多帧图像 WebSocket payload 大 4 帧 × 3 相机 × 640×480×3 原始图像 payload 很大，会放大网络和序列化开销。 支持 --image-transport jpeg 和质量参数；server 端支持 JPEG sequence 解码，并记录 raw/tx payload。 每步日志可直接比较 raw payload 与 transmitted payload。
异步推理效果变差 投机预取会提前推进有状态 action head 的 causal cache；如果结果过期或被拒绝，主 cache 可能已经被污染。 实现 speculative 框架但默认关闭；加入边界状态 drift、age、ready-at-boundary 检查；面试中明确说明需要独立 cache/rollback 才能做严格异步。 展示你不是盲目打开论文功能，而是识别了 stateful cache 的系统风险。
抓取空抓、高度不准、软物体夹坏 关节空间误差会放大到末端高度；gripper close 值对纸杯/餐巾纸这类软物体很敏感。 基于 action log 分析抓取时刻、关节趋势和 gripper 变化；增加 --gripper-closed-value，并提出高度补偿/normalization stats/推理步数对比方案。 能把失败拆成视觉规划、动作映射、执行接触高度、夹爪策略四类，而不是只说“模型不好”。

direct-48 模式把一个 action chunk 按 30Hz 执行，理论时长 48 / 30 = 1.6s。

1.60s

日志中流式执行时长稳定约 1.60s，完整 chunk 约 1.80s。

修复 4-step 生效后，服务端稳态推理曾记录约 2.6-3.0s。

面试中要主动说明边界：这套工程已经把执行侧对齐到论文的 48-step/30Hz，但完整闭环还没达到论文 Flash/GB200 级别的 7Hz。当前瓶颈主要在模型推理时延、真正异步 cache 隔离和 Flash/TensorRT/低层 kernel 优化。

面试表达建议

一分钟版本

我主要补齐了 DreamZero 到 AgiBot 真机的完整推理闭环。论文给出 WAM 机制和权重，但真机要解决 server/client 协议、三路相机与 proprio 的模态映射、双臂 22 维动作解析、GDK 单位和左右臂顺序、48-step chunk 按 30Hz 执行、cache reset、视频和动作日志诊断等问题。我最后把系统做成可启动、可复现、可调参的 server/client，并通过日志定位出当前主要瓶颈从执行侧转移到推理侧。

技术亮点版本

我比较深入的点是没有把模型当黑盒。DreamZero 是 stateful autoregressive diffusion policy，内部 KV cache 会跨 chunk 影响结果，所以 session/reset/投机推理都不能简单处理。我修了推理步数和 DiT step mask 的一致性问题，也识别了 speculative inference 会污染主 cache 的风险，因此默认保守关闭，后续需要独立 cache 或 rollback 机制。这类问题比写一个 WebSocket client 更关键。

STAR 回答模板

问题 回答结构
你最大的工作量是什么？ S：官方没有 AgiBot 真机 server/client。T：要把论文权重变成真机闭环。A：补 wrapper、协议、GDK client、direct-48 执行、日志、cache reset。R：能连续推理、执行、保存 action JSON 和生成视频，执行节奏对齐 48/30Hz。
你遇到最难的问题是什么？ 不是单个 bug，而是多层语义错位：模型输出是 relative 还是 absolute、SDK 单位是否一致、动作是否被 Ruckig 改坏、cache 是否被跨任务污染。我的方法是把链路拆成五层并逐层加日志。
为什么 direct-48 重要？ 论文假设每个 action chunk 是 48 step、30Hz、1.6 秒。如果 client 把 48 行动作重插值成长轨迹，就破坏了训练/推理时序。direct-48 让真实执行更接近模型的 action horizon。
为什么没有直接开异步？ DreamZero 的 action head 有 KV cache。投机推理如果写入主 cache，而结果最后被拒绝，就会让后续同步推理看到错误历史。所以我先实现框架和状态检查，但默认关闭；严格方案应做分支 cache 或 rollback。
为什么推理还达不到论文 7Hz？ 论文 7Hz 依赖完整系统优化和 Flash/量化/kernel 路线。我的版本在现有硬件和开源代码基础上完成真机闭环与关键一致性修复，执行侧已对齐 1.6s，剩余瓶颈是推理侧，需要进一步做 Flash/TensorRT/独立 cache 异步。

后续路线图

  1. 推理分项 metrics 入 JSON：把 server 的 Text/Image/VAE/KV/Diffusion/DIT Compute Steps 写到每步记录中，减少人工读日志。
  2. 观测 ablation：在同一场景对比 4帧@5FPS、1帧@30FPS、9帧@30FPS 的生成视频、动作质量和推理时延。
  3. 安全异步：实现 speculative branch cache 或 cache rollback，避免预取污染主 causal state。
  4. 推理优化：评估 Flash/1-step、TensorRT、scheduler GPU 化、低精度量化；目标是让推理低于 1.6s chunk 时长。
  5. 任务级 benchmark：固定 prompt、物体位置、起始姿态，统计抓取/放置/擦拭成功率，而不是单次主观判断。
  6. 执行一致性日志：可选开启 row-level log，并以低频读回状态验证 SDK 是否跟上 30Hz row target。
